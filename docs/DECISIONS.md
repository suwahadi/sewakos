# DECISIONS.md — Catatan keputusan teknis kecil

> Keputusan teknis kecil (nama paket, struktur internal) yang tidak mengubah kontrak API, skema yang sudah
> di-push, atau perilaku uang (SPEC-GO.md §0.5). Keputusan yang lebih besar tetap lewat AGENT.md §3
> (berhenti dan tanyakan pemilik).

| Tanggal | Keputusan | Alasan |
|---|---|---|
| 2026-11-10 | `.githooks/pre-commit` menambah guard `[ -f backend/go.mod ]` / `[ -f frontend/package.json ]` sebelum menjalankan cek Go/npm | AGENT.md §8.2 menjalankan `npm run typecheck`/`go vet` begitu ada perubahan di `backend/`/`frontend/`, termasuk sebelum B1.1/F0.1 membuat proyeknya; tanpa guard, commit R0.3 (`frontend/.env.example`) gagal karena `package.json` belum ada. Perilaku cek untuk proyek yang sudah ada tidak berubah. |
| 2026-11-10 | Migration goose dijalankan lewat `go run github.com/pressly/goose/v3/cmd/goose@<versi>` (bukan `go get -tool`) | `cmd/goose` meng-import semua driver DB yang didukungnya (ClickHouse, MySQL, MSSQL, SQLite, YDB, dll.); memasangnya sebagai tool di `go.mod` menarik puluhan dependency transitif di luar SPEC-GO.md §3. `go run pkg@versi` tetap memanggil goose tanpa menyentuh `go.mod`/`go.sum` modul ini. Tidak ada `cmd/migrate` di pohon SPEC §3, jadi ini jalur resmi menjalankan migration. |
| 2026-11-10 | Password role `kos_app` tidak ditaruh di migration; migration hanya `CREATE ROLE ... LOGIN` tanpa `PASSWORD` | AGENT.md §5.3 melarang commit rahasia. Password diisi terpisah (`ALTER ROLE kos_app WITH PASSWORD '...'`) oleh operator/deploy, bukan dari source yang di-commit. |
| 2026-11-10 | `sqlc` dijalankan lewat `go run github.com/sqlc-dev/sqlc/cmd/sqlc@<versi>` (bukan `go get -tool`), schema sqlc dibaca dari `db/schema.sql` yang di-generate `scripts/gen-sqlc-schema.sh`, bukan langsung dari `db/migrations/*.sql` | Sama alasannya dengan goose: `go get -tool` sqlc menarik dependency besar ke go.mod. Lebih penting: file migration goose menaruh Up **dan** Down dalam satu file; sqlc membaca seluruh file secara berurutan, jadi tanpa pemisahan ini DROP TABLE di blok Down akan "mengosongkan" katalog yang baru dibuat blok Up-nya sendiri. Jalankan ulang skrip itu setiap mengubah migration, sebelum `sqlc generate`. |
| 2026-11-10 | Validasi (`internal/validation`) memanggil `validator.Var(...)` satu rule sekaligus per field, bukan struct tag berantai (`validate:"required,min=3,max=5"`) | Diuji langsung: `go-playground/validator/v10` berhenti di rule pertama yang gagal untuk satu field, apa pun rule-nya — bukan hanya `required`/`accepted` seperti yang diminta SPEC-GO.md §5.4 ("rule lain tetap dicek dan semua yang gagal dilaporkan"). Memanggil `Var` per-rule memberi kendali urutan dan akumulasi error yang persis sesuai tabel pesan. |
| 2026-11-10 | `money.WIB` memakai `time.FixedZone` (offset tetap +7), bukan `time.LoadLocation("Asia/Jakarta")` | Indonesia tidak pernah menerapkan DST, jadi offset tetap sudah 100% benar, dan tidak bergantung pada paket `tzdata` yang mungkin tidak terpasang di image runtime minimal (`debian-slim`). |
| 2026-11-10 | `POST /auth/login` (API.md §2.4) diimplementasikan di B1, lebih awal dari jadwalnya (B2.1) | B1.10 mensyaratkan "satu contoh fixture dari API.md berjalan hijau", tapi sebelum B2 belum ada endpoint nyata untuk diuji end-to-end. Login dipilih sebagai irisan vertikal minimal (token issuance sudah ada dari B1.6). Sisa cakupan B2.1 (registrasi, OTP, dsb.) belum dikerjakan dan tetap tugas B2. |
| 2026-11-10 | `cmd/seed` idempoten lewat early-exit (cek area `kota-depok` sudah ada → keluar tanpa apa-apa), bukan upsert per baris | Dataset seed kecil dan sebagian besar tabelnya (`rooms`, `user_notifications`) tidak punya kolom unik alami untuk di-`ON CONFLICT`. Early-exit cukup untuk kebutuhan dev/test "jalankan sekali, tidak error bila dijalankan lagi"; tidak merekonsiliasi perubahan parsial. |
| 2026-11-10 | Limiter `api` dan `otp` berbagi satu primitive `internal/platform/ratelimit.Allow` (fixed-window Redis INCR+EXPIRE) | SPEC-GO.md §5.1 menyebut keduanya sama arsitekturnya (window tetap, kunci Redis beda: per-IP untuk `api`, per-nomor-tujuan untuk `otp`). `api` sudah dipasang sebagai middleware HTTP sekarang (B1.6); `otp` baru benar-benar dipakai saat endpoint OTP ada (B2.1) — primitive-nya sudah siap, pemanggilannya menyusul. |
| 2026-11-10 | Tidak ada middleware terpisah "cek akun dinonaktifkan" | Suspend (API-ADMIN.md §3) menghapus semua `access_tokens` user itu dalam transaksi yang sama; begitu disuspend, tidak ada token valid yang tersisa untuk diverifikasi, jadi jalur `RequireAuth` yang sudah ada (401 sesi tidak valid) otomatis menutup celah ini tanpa pengecekan `suspended_at` terpisah di tiap request. |
| 2026-11-10 | `eslint.config.mjs` mengimpor `eslint-config-next/core-web-vitals` dan `eslint-config-next/typescript` langsung, bukan lewat `FlatCompat` | `FlatCompat` (dari `@eslint/eslintrc`) mengasumsikan config lama (eslintrc), lalu mencoba memvalidasi hasil `extends` sebagai objek legacy; `eslint-config-next@16` sudah mengekspor array flat config asli, dan validator `FlatCompat` gagal (`Converting circular structure to JSON`) karena objek plugin React mereferensikan dirinya sendiri di `configs.flat`. Impor langsung menghindari lapisan kompatibilitas yang tidak dibutuhkan. |
| 2026-11-10 | 8 advisory moderate (ReDoS `minimatch` lewat `typescript-eslint`→`@typescript-eslint/typescript-estree`) dibiarkan, tidak di-force-fix | Hanya dependensi dev-time milik `eslint-config-next@16.4.6`; perbaikan non-breaking belum tersedia (`npm audit fix` tidak mengubah apa pun), perbaikan penuh butuh `eslint-config-next@>=15.6.0-canary.0` (rilis canary, breaking). Tidak memengaruhi kode yang dikirim ke pengguna. Tinjau ulang saat `eslint-config-next` merilis versi stabil yang memperbaikinya. |
